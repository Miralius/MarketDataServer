# Функциональные требования

MarketDataServer — веб сервер на C++23, Boost и gRPC для асинхронной обработки Bloomberg-подобных запросов. Поддерживает только request/response; подписки и REST API не входят в объём работ. Форматы сообщений, статусы и ошибки определены в [protobuf-контракте](api/market_data.proto).

1. `MarketDataService` должен предоставлять gRPC-методы `Submit`, `GetResult` и `Health`.
2. `SubmitRequest` должен содержать ровно один из двух типов запроса: `ReferenceDataRequest` или `HistoricalDataRequest`; их поля и ограничения описываются в [protobuf-контракте](api/market_data.proto).
3. `RequestValidator` должен проверять запрос до регистрации задания; ошибка одного запроса не должна влиять на ранее принятые задания.
4. `Submit` должен зарегистрировать задание и без ожидания биржи вернуть уникальный `job_id` и начальный статус; конкурентные обновления должны быть согласованными, а `COMPLETED` публикуется только после сохранения результата. Жизненный цикл описан в [protobuf-контракте](api/market_data.proto).
5. Задания должны передаваться worker-потокам через ограниченную MPMC `boost::lockfree::queue`, содержащую только лёгкие идентификаторы работы.
6. Если очередь заполнена, новый запрос должен быть отклонён с `RESOURCE_EXHAUSTED` без создания незавершённой записи в хранилище.
7. Если данные ещё не готовы, сервер должен опрашивать биржу неблокирующим таймером `Boost.asio` до готовности, ошибки или общего deadline. Параметр `poll_interval` задаётся конфигурацией процесса, по умолчанию равен 1 секунде и используется также как интервал retry.
8. При временной сетевой или транспортной ошибке provider-операции, включая gRPC `UNAVAILABLE` и эквивалентные ошибки адаптера, сервер должен повторить ту же операцию не более `max_transient_retries` раз; значение задаётся конфигурацией и по умолчанию равно 3. Счётчик последовательных transient-ошибок сбрасывается после успешного provider response, а общий deadline имеет приоритет над retry budget. Permanent provider errors и ошибки содержимого протокола повторяться не должны.
9. Retry не должен менять публичный `job_id` или создавать у поставщика дубликат операции. После четвёртой последовательной transient-ошибки при значении по умолчанию задание должно перейти в `FAILED` с `ERROR_CODE_PROVIDER_UNAVAILABLE`. При transient-ошибке потокового получения данных сервер должен удалить частично сохранённые staging chunks и повторить чтение с chunk 0.
10. PostgreSQL должен быть единым постоянным хранилищем запросов, статусов, счётчика последовательных retry и порций ответов.
11. Перед обращением к бирже сервер должен искать в PostgreSQL завершённый результат для точно такого же нормализованного запроса и при совпадении использовать его повторно.
12. `GetResult` должен сообщать metadata и текущий статус незавершённого задания, а для завершённого — потоково выдавать сохранённые порции; сериализованный `ResultChunk` не должен превышать 1 Мб. Пустой ответ допустим.
